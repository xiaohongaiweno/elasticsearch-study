## 一、先想清楚：为什么要读源码

作为云服务工程师，你读源码的目的和「编译器工程师」不同。你的目标只有四个：

| 目的 | 具体场景 | 需要的源码深度 |
| --- | --- | --- |
| **① 定位问题** | 客户集群写入变慢 / 出现 `UnassignedShard` / 频繁 GC / 查询超时 | 能顺着调用链走到「哪一步耗时/抛异常」，能读懂日志与 Stats 字段的来源 |
| **② 解释行为** | 客户问「为什么我的 bulk 返回 429」「为什么 `wait_for_active_shards` 没生效」 | 能指到具体代码行，讲清判定条件 |
| **③ 改造源码** | 加内部监控埋点、改分配策略、加自定义 REST 接口、调优合并策略 | 能改一个模块而不破坏其它模块 |
| **④ 写扩展** | 自研插件：自定义分析器、自定义 Repository、自定义 Ingest Processor | 熟悉 Plugin / Module / 扩展点注册机制 |

**因此本路线的侧重点是：调用链 + 判定条件 + 可观测点**，而不是「算法原理推导」。
倒排索引原理、BM25 公式、Lucene 段合并算法这些属于 Lucene 范畴，了解即可，不作为主线。

## 二、前置知识自查（动手前必须过这一关）

读 ES 源码前，请确认你自己打分 ≥ 7 分（满分 10）：

### 2.1 Java 语言能力

- [ ] **泛型与通配符**：ES 大量使用 `Supplier<Request>`、`ActionListener<Response>`、`CheckedBiConsumer`。看不懂 `<? super T>` 会很痛苦。
  入口：`server/src/main/java/org/elasticsearch/action/ActionListener.java`、`server/src/main/java/org/elasticsearch/common/CheckedConsumer.java`
- [ ] **函数式接口与 Lambda**：`executor.execute(() -> doSomething())` 遍地都是。
- [ ] **并发包**：`AtomicLong`、`ConcurrentHashMap`、`CountDownLatch`、`CompletableFuture`（ES 6.x 用得较少，主要是自研的 listener 链）、`ReentrantLock`。
- [ ] **NIO/Netty 基础**：`EventLoopGroup`、`ChannelPipeline`、`ByteBuf`、`ChannelHandler`。ES 的网络层完全建立在 Netty 之上。
- [ ] **反射与 ClassLoader**：插件加载依赖 `URLClassLoader`，见 `server/src/main/java/org/elasticsearch/plugins/PluginsService.java`。
- [ ] **JVM 基础**：堆/栈、GC（ES 最常被问的就是 GC）、直接内存、`-XX:+UseConcMarkSweepGC`（6.x 默认 CMS）。

### 2.2 分布式系统基础

- [ ] **Paxos/Raft 的基本思想**：ES 6.6 用的是自己的一套「类 Paxos」选主（ZenDiscovery + 最小 master 节点数仲裁），不实现完整 Raft，但要理解「quorum」「脑裂」「任期」。
- [ ] **主从复制（primary-replica）**：写请求先写主分片再复制到副本分片，返回时机取决于副本是否 ack。
- [ ] **一致性模型**：ES 6.x 提供的是「最终一致 + 可选强一致读（通过 seqno + primary term）」。要区分 `refresh` 语义与「写入成功」语义。
- [ ] **两阶段提交**：ES 的集群状态发布是「master 计算 → 广播 → 各节点 ack」的两阶段。

### 2.3 Elasticsearch 使用能力

- [ ] 熟练使用 REST API：`_bulk`、`_search`、`_cat/shards`、`_cluster/state`、`_nodes/stats`
- [ ] 理解以下概念并能画图：cluster / node / index / shard / replica / segment / translog / mapping / analyzer
- [ ] 理解 `refresh_interval`、`number_of_shards`、`routing`、`_source`、doc values

### 2.4 工具能力

- [ ] IntelliJ IDEA 使用（Go to Implementation、Find Usages、Diagram、Call Hierarchy）
- [ ] Gradle 基础（知道 `./gradlew :server:compileJava` 在干什么）
- [ ] 能用 `jstack` / `jmap` / `arthas` 抓现场（这对线上问题定位极其重要）

> **如果 2.3、2.4 有任何一项没达标，先补到能画图再开始读源码。**
> 否则你会陷入「代码能看懂字面意思，但不知道它在整个系统里的位置」的困境。

### 5.4 关键调用链（务必手画一遍）

**链 A：REST 请求进入**
```
Netty4HttpRequestHandler.channelRead0
  → Netty4HttpServerTransport.dispatchRequest
  → RestController.dispatchRequest (RestController.java:168)
      → 按 method + path 匹配 RestHandler（RestController.registerHandler :151）
      → handler.handleRequest(request, channel, client)
      → BaseRestHandler 包装（参数消费校验 + 异常转换）
```

**链 B：本地执行 Transport Action（以 index 为例）**
```
RestIndexAction.prepareRequest → client.index(req, listener)
  → NodeClient.index → AbstractClient.index → execute(IndexAction.INSTANCE, request, listener)
  → NodeClient.executeLocally(action, request, listener)
      → TransportAction: transportService.sendRequest(localNode, actionName, request, options, handler)
      → TcpTransport 直接走 local handler（不发网络包）
  → TransportIndexAction.doExecute
      → TransportReplicationAction.doExecute（:171）→ ReplicationOperation
```

**链 C：Transport 跨节点 RPC**
```
发送方：
  TransportService.sendRequest (TransportService.java:512/524/537)
    → sendRequestInternal (:597)
      → Transport.sendRequest → TcpTransport.sendRequest (TcpTransport.java:280)
        → 序列化 header + request → channel.writeAndFlush
接收方（Netty 线程）：
  Netty4MessageChannelHandler.channelRead → TcpTransport.messageReceived (TcpTransport.java:1071)
    → 读 header（requestId / status / version）
    → 若 status == request：handleRequest (:1215)
        → 找到 RequestHandlerRegistry（getRequestHandler :1506）
        → 用 handler 的线程池 execute 到业务线程池
        → TransportRequestHandler.messageReceived(request, channel, task)
    → 若 status == response：handleResponse (:1163)
        → responseHandlers 里取 TransportResponseHandler → handler.handleResponse
```

## 六、阶段 2：集群期（第 4~5 周）——状态、选主、分配

### 6.1 本阶段目标

理解 ES 的「元数据大脑」：
**集群状态是什么 → 谁能改它 → 怎么保证所有节点看到同一份 → 分片怎么被决定放在哪台机器**。

### 6.2 核心问题清单

- `ClusterState` 包含哪些东西？为什么它被设计为「不可变 + 全量广播」？
- `Diff` 机制解决了什么性能问题？
- Master 节点为什么不用锁，却能保证状态更新串行？
- 为什么 ES 6.6 要检查「最小 master 节点数」，它防的是什么？
- 分片的分配决策是怎么做出来的？为什么有的分片一直 unassigned？
- `MetaData` 和 `ClusterState`、`RoutingTable` 是什么关系？

### 7.5 抽象出的一张「写入状态图」

```
 请求到达
    │
    ├─ 索引不存在 & action.auto_create_index=true → 创建索引（走集群状态线）
    │
    ├─ 目标 shard 不在本节点 → 转发（TransportActionNodeProxy）
    │
    ├─ shard 不是 STARTED 状态
    │     → IndexShardNotStartedException → 重试或失败（retry_on_failure 逻辑在 ReplicationOperation）
    │
    ├─ routing 找不到（无 primary 活跃）
    │     → UnavailableShardsException
    │
    ├─ 版本冲突
    │     → VersionConflictEngineException（HTTP 409）
    │
    ├─ 全部 item 失败 & 没有成功的 → BulkResponse.hasFailures = true，HTTP 200（★ 重要！）
    │
    └─ 成功 → 更新 checkpoint → 返回 BulkResponse
```

**链 F：Query Then Fetch（默认搜索模式）**
```
RestSearchAction → client.search → TransportSearchAction.doExecute（:380/:177）
  → 解析 SearchSourceBuilder（server/src/main/java/org/elasticsearch/search/builder/SearchSourceBuilder.java）
  → 解析 IndexNameExpressionResolver 得到目标索引
  → 计算目标 shard 列表（IndexShardRoutingTable，过滤不可用副本 → 优先本地）
  → executeSearch（:291）：
      → 选 SearchType：QUERY_THEN_FETCH / DFS_QUERY_THEN_FETCH
      → new SearchQueryThenFetchAsyncAction(...).start()
        → AbstractSearchAsyncAction.start()（:112）
          → executePhase(QUERY_PHASE)（:158）→ 向 N 个 shard 并发发 QuerySearchRequest
            每 shard 端：
              SearchService.executeQueryPhase → QueryPhase.execute（QueryPhase.java:95）
                → QueryShardContext.toQuery → Lucene Query
                → 创建 Collector（TopScoreDocCollector / TopFieldCollector）
                → Lucene IndexSearcher.search
                → 得到 TopDocs + 每个 doc 的 sort values + 打分统计
              → QuerySearchResult 返回给协调节点
          → 所有 shard 返回后 → onShardSuccess（:237）收集
          → executePhase(FETCH_PHASE)（:158）
              、先 SearchPhaseController 归并（选全局 top size 个 docId）
              → 向「持有这些 docId 的 shard」发 FetchSearchRequest

**链 G：聚合的归并**
```
每个 shard：QueryPhase 内 → 创建 Aggregator 树 → collect 到 InternalAggregation（每个 shard 一份部分结果）

## 十、读源码的方法论（比路线更重要）

### 10.1 三遍阅读法

对每一个模块，都要读三遍，每遍目标不同：

| 遍数 | 目标 | 做法 | 耗时占比 |
| --- | --- | --- | --- |
| 第 1 遍 | **建立地图** | 只看类名、方法名、注释、接口定义。**不读方法体**。画出类之间的关系 | 20% |
| 第 2 遍 | **抓主流程** | 找入口方法，用 IDE 的 Call Hierarchy 顺主干走。跳过所有 catch 分支和边界处理 | 40% |
| 第 3 遍 | **抠细节** | 逐行读主干上的每个方法，特别关注 if 判断条件、异常分支、并发控制 | 40% |

**绝对不要第一遍就逐行读 InternalEngine.java（142KB）**，你会崩溃。

### 10.2 四个必备的提问习惯

读每一段代码，都问自己：

1. **这段代码在什么线程上执行？**（ES 是多线程的，线程错了，理解全错）
2. **这个对象的生命周期由谁管？**（谁 new 的、谁 close 的）
3. **这个状态变更会不会被广播出去？**（影响集群需要走集群状态线）
4. **失败路径是什么？**（ES 的健壮性全在失败路径里，只读成功路径等于没读）

### 10.3 用好 IDE 的四个功能

- **Call Hierarchy（Ctrl+Alt+H）**：看一个方法被谁调用。这是找入口的最快方式。
- **Find Usages（Alt+F7）**：找一个类被谁使用。定位扩展点必备。
- **Type Hierarchy（Ctrl+H）**：看接口的实现类。ES 大量使用接口+多实现。
- **Diagrams（右键 → Diagrams → Show Diagram）**：对 `Engine`、`Aggregator` 这类继承体系极其有用。

### 10.4 画图是唯一有效的学习方式

每读完一个模块，**必须**画一张图，否则等于没读。建议的图清单：

- [ ] 节点启动时序图
- [ ] 一次 bulk 写入的完整时序图（含线程切换）
- [ ] Engine 接口体系类图
- [ ] ClusterState 的字段结构图（MetaData / RoutingTable / DiscoveryNodes）
- [ ] 分片分配决策流程图（含 Decider 链）
- [ ] Query Then Fetch 时序图
- [ ] 聚合的 reduce 树形图
- [ ] Translog / Lucene / Checkpoint 三者的关系图

### 10.5 善用「对照法」

- **对照日志读代码**：把日志级别调到 `DEBUG`（`logger.org.elasticsearch.transport=DEBUG`），
  让日志告诉你代码走到了哪，再回去读。比盲读快 10 倍。
- **对照 `_cat` API 读代码**：每个 `_cat` 字段背后都是一个 Java 字段。
- **对照测试读代码**：`server/src/test/java/org/elasticsearch/...` 下的测试类是最好的使用文档。
  例如想知道 `InternalEngine` 怎么用，直接读 `InternalEngineTests.java`。

## 十二、各阶段自测题库

（各阶段的自测题已分散在对应章节。这里给出**跨阶段综合题**，能答对说明你真正掌握了 ES。）

**综合题 1**：客户说「写入成功了，但马上查询查不到」。请给出至少 3 种可能原因，并分别指出源码中的判定位置。

<details>
<summary>参考答案要点</summary>

1. **refresh 还没发生**：写入只进 `Translog` + Lucene memory buffer，需要 refresh 才可见。源码：`IndexShard.refresh`（:918）、`InternalEngine.refresh`（:1596）、`IndexSettings.INDEX_REFRESH_INTERVAL_SETTING`。
2. **读请求打到了不同副本**：副本的 refresh 是独立的（虽然通常是同时的），且副本 if 有 lag。源码：`ReplicationTracker` 的 checkpoint。
3. **查询走的是非 realtime 路径**：`GET /_search` 不走 realtime，而 `GET /index/type/id` 走 realtime（`IndexShard.get` :910 → `InternalEngine.get` :616，会先查 `LiveVersionMap` 再查 translog）。
4. （bonus）**请求打到了没有该分片的节点但用了 `preference`**，或**跨集群/CCR 场景下 follower 落后**。
</details>

**综合题 2**：3 个数据节点，索引 1 主 2 副。kill 掉 1 个节点后，集群发生了什么？请按时序列出涉及的类和状态变更。

<details>
<summary>参考答案要点</summary>

1. `NodesFaultDetection` 检测到节点断开 → 通知 `ZenDiscovery.handleNodeFailure`（`ZenDiscovery.java:679`）
2. 若 master 挂了 → `MasterFaultDetection` 触发重新选主（`ZenDiscovery.findMaster` :899）
3. 新 master 提交 ClusterState 任务：`AllocationService.disassociateDeadNodes` + `reroute`（:360）
4. 该节点上的分片变为 `UNASSIGNED`，`UnassignedInfo.reason = NODE_LEFT`
5. `GatewayAllocator` 找到新的可用节点 → `BalancedShardsAllocator.allocate`
6. 新分片 `INITIALIZING` → `RecoverySourceHandler.phase1`（:288）从主分片拷贝 segment
7. 本地 checkpoint 追上 → `finalizeRecovery`（:486）→ 分片 `STARTED`
8. 期间 `ClusterState` 版本号递增多次，每次都会广播到所有节点
</details>

**综合题 3**：`_bulk` 请求返回 `"errors": false`，但客户说少了几条数据。可能吗？为什么？

<details>
<summary>参考答案要点</summary>

可能。`BulkResponse.hasFailures()` 的判定是「是否有 item 失败」（`BulkResponse.java`）。
但以下情况不会体现在 errors 里：
1. **`_routing` 配置不同**导致文档被路由到 `_routing` 指定的分片，客户按默认路由查不到。
2. **文档被 pipeline drop 了**：Ingest pipeline 中 `drop` processor 会静默丢弃（`IngestService.innerExecute`，`itemDroppedHandler`）。
3. **自动创建索引时 mapping 不完全一致**导致字段被忽略（`dynamic: false`）。
4. **CCR/跨集群**场景 follower 落后。
5. **多线程 bulk 中，client 侧解析响应丢失**。
</details>

**综合题 4**：为什么 ES 的 `from + size` 有 10000 的限制？`search_after` 为什么没有？

<details>
<summary>参考答案要点</summary>

`from + size` 需要每个分片都返回 `from + size` 个命中，协调节点做归并，内存和 CPU 开销随 from 线性增长（`SearchPhaseController` 的归并需要持有全部候选）。
`search_after` 利用排序值做「游标」，每个分片只需返回 size 个比游标大的命中，内存恒定。
源码：`SearchSourceBuilder` 中的 `MAX_RESULT_WINDOW` 校验、`SearchAfterBuilder`、`TopFieldCollector`。
</details>

**综合题 5**：Translog 和 Lucene commit 的关系是什么？为什么 ES 不能只依赖 Lucene？

<details>
<summary>参考答案要点</summary>

Lucene 的 `commit` 是昂贵的（要在 `segments_N` 上 fsync 并同步所有文件）。
如果每次写入都 commit，写入吞吐会崩掉。所以 ES 引入 Translog：
每个写入操作先 append 到 translog（顺序写，快），Lucene 侧只做 in-memory add。
只有当 `flush`（默认条件：translog 大小达阈值 / 显式调用）时，才做一次 Lucene commit + translog generation 滚动。
宕机恢复时：从最后一个 Lucene commit 点开始，重放 translog 中未 commit 的操作。
源码：`InternalEngine.flush`（:1743）、`InternalEngine.commitIndexWriter`（:2387）、`Translog.rollGeneration`（:1702）、`Checkpoint.java`。
</details>

## 十三、常见踩坑与避坑指南（6.6.1 专属）

### 13.1 版本陷阱

| 陷阱 | 说明 |
| --- | --- |
| **到处找 `BulkRequestParser`** | 6.6.1 **没有这个类**。bulk 的 NDJSON 解析在 `BulkRequest.add(...)` 内部。这个类在 7.x 才被抽出。 |
| **到处找 `FsyncPolicy`** | 6.6.1 用的是枚举 `Translog.Durability { ASYNC, REQUEST }`（`Translog.java:1571`）。`FsyncPolicy` 是 7.x 的东西。 |
| **到处找 `SequenceNumbersService`** | 6.6.1 没有这个类。相关能力分散在 `SequenceNumbers`（常量）、`LocalCheckpointTracker`（追踪）、`ReplicationTracker`（全局检查点）。 |
| **以为 6.6 没有 seqno 复制** | **错**。6.6 已有完整的 `ReplicationTracker`（约 47KB）和 `ReplicationGroup`，支持 local/global checkpoint、in-sync allocation tracking、primary relocation handoff。 |
| **以为 6.6 用 Raft** | 6.6 用 **ZenDiscovery**（`discovery/zen`），不是 Raft，也没有 7.x 的 `CoordinationService`。 |
| **以为 ES 6.6 不用 Guice** | 6.6 **还在用**：`Node.java:603` → `ModulesBuilder.createInjector()`。7.x 才移除。 |
| **找 `IndexMetaData` 叫 `IndexMetadata`** | 6.6 是 `IndexMetaData`（大写 D）；7.x 才改成 `IndexMetadata`。同理 `MetaData` vs `Metadata`。 |

### 13.2 阅读陷阱

| 陷阱 | 说明 |
| --- | --- |
| **从 `InternalEngine.java` 开始读** | 142KB / 几千行，读了必崩。应该从 `Engine` 接口（75KB，但结构清晰）开始。 |
| **忽略线程切换** | ES 的代码跨很多线程池，一个方法调用返回时可能已经换了线程。看到 `executor.execute(...)` 就要警觉。 |
| **忽略异步** | ES 大量使用 `ActionListener` 回调，**方法返回不代表操作完成**。这是初学者最大的坑。 |
| **只读 server 模块** | Netty 实现在 `modules/transport-netty4`，HTTP 也是；分析器在 `modules/analysis-common`；脚本在 `modules/lang-painless`。 |
| **忘记看测试** | `server/src/test/java/...` 下的测试是最好的文档。`InternalEngineTests`、`AllocationServiceTests`、`TransportBulkActionTests` 都值得读。 |
| **掉进 `common/inject` 的兔子洞** | 那是 Guice 的 fork，读它对理解 ES 毫无帮助。只需要知道 `ModulesBuilder` + `Module` + `@Inject` 的用法即可。 |

### 13.3 排障陷阱

| 陷阱 | 说明 |
| --- | --- |
| **以为 `_bulk` 返回 200 就是全部成功** | 必须检查 `"errors": true` 和每个 item 的 `status`。 |
| **以为写入成功 = 立刻可查** | 需要 `refresh`。`GET /index/type/id` 是 realtime 的，`_search` 不是。 |
| **以为 `wait_for_active_shards` 默认是 all** | 默认是 `1`（primary 写成功即返回）。 |
| **以为副本失败会回滚** | 不会。primary 写成功后即返回，副本失败只会标记 replica failed 并触发恢复。 |
| **忽略 `unassigned` 的 `DelayedAllocationService`** | 节点离开后分片不会立刻重新分配，默认延迟 1 分钟（`index.unassigned.node_left.delayed_timeout`）。 |
| **以为 `cluster.routing.allocation.disk.watermark` 是实时的** | 它依赖 `ClusterInfoService` 的周期性刷新（默认 30s）。 |

## 十四、进阶方向（学完之后往哪走）

按难度排序，建议逐个攻破：

1. **CCR（跨集群复制）** — `x-pack/plugin/ccr`
   这是理解 seqno / global checkpoint / translog 最好的实战材料。
   必读：`CcrFollowTask`、`ShardFollowTask`、`ShardFollowNodeTask`。

2. **ILM（索引生命周期管理）** — `x-pack/plugin/ilm`
   55 个 java 文件，规模适中，能学到「如何基于 ClusterState 实现一个声明式的状态机」。

3. **SQL 引擎** — `x-pack/plugin/sql`
   822 个文件，能学到「如何把 SQL 编译成 ES Query DSL」。
   重点看 `SqlParser`、`QueryTranslator`、`ExpressionAnalyzer`。

4. **Aggregation 框架深入** — `server/src/main/java/org/elasticsearch/search/aggregations`
   426 个文件。理解 `AggregatorFactory` 注册机制、`InternalAggregation.reduce` 的各种实现。

5. **合并策略与写入性能** — `EsTieredMergePolicy`、`ElasticsearchConcurrentMergeScheduler`、`MergePolicyConfig`
   这是云服务性能调优的核心。

6. **自研插件** — 从 `plugins/examples` 出发，做一个对你业务有用的插件。

7. **源码级改造** — 例如：
   - 在写入链路上加自定义埋点（`IndexingOperationListener`）
   - 实现自定义 `AllocationDecider`（比如按机房亲和性）
   - 实现自定义 `Repository`（对接你公司内部的存储系统）

8. **跨版本对比阅读** — 读完 6.6.1 后，读 7.x 的同一模块，理解：
   - 为什么移除 Guice
   - 为什么 `ZenDiscovery` 被 `CoordinationService` + Raft 替换
   - `seqno` 复制状态机的演进（`CheckpointState` 重构）
   - `IndexMetaData` → `IndexMetadata`
