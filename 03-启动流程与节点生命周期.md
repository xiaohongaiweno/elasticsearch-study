# 03 · 启动流程与节点生命周期

> 目标：逐行走完 `Elasticsearch.main` → `Bootstrap` → `Node` 构造 → `Node.start()` → `Node.close()`，
> 知道每个阶段做了什么、依赖了谁、失败会怎样。

## 1. `Elasticsearch.main`：进程的第一行代码

文件：`server/src/main/java/org/elasticsearch/bootstrap/Elasticsearch.java`

```java
public static void main(final String[] args) throws Exception {      // :76
    overrideDnsCachePolicyProperties();                              // :77
    // 先装一个"什么都允许"的桩 SecurityManager，
    // 目的是让 JVM 相信有 SM，从而立即生效 networkaddress.cache.ttl 这类策略
    System.setSecurityManager(new SecurityManager() {                // :83
        @Override public void checkPermission(Permission perm) { }
    });
    LogConfigurator.registerErrorListener();                         // :91
    final Elasticsearch elasticsearch = new Elasticsearch();          // :92
    int status = main(args, elasticsearch, Terminal.DEFAULT);         // :93
    if (status != ExitCodes.OK) { exit(status); }
}
```

**为什么要先装桩 SecurityManager？**
因为 JVM 的 DNS 缓存策略（`networkaddress.cache.ttl`）只在「有 SecurityManager」时才严格生效。
ES 后面会换成自己的 `Security`（`bootstrap/Security.java`），但那时 DNS 策略已经太晚了。

**`execute` 方法（:120）**：
- 打印版本（`--version`）
- 支持 `--daemonize` / `--pidfile` / `--quiet`
- `env.validateTmpFile()`（`:144`）：`java.io.tmpdir` 配错会导致后面一堆诡异问题，所以直接拒绝启动
- 调 `init(...)`（`:156`）→ `Bootstrap.init(...)`

### 2.1 `Bootstrap.setup`（`:161`）——真正危险的部分

```java
private void setup(boolean addShutdownHook, Environment environment) throws BootstrapException {
    Settings settings = environment.settings();                              // :162
    spawner.spawnNativeControllers(environment);                             // :165

    initializeNatives(                                                        // :170 → :98
        environment.tmpFile(),
        BootstrapSettings.MEMORY_LOCK_SETTING.get(settings),                 // bootstrap.memory_lock
        BootstrapSettings.SYSTEM_CALL_FILTER_SETTING.get(settings),          // bootstrap.system_call_filter
        BootstrapSettings.CTRLHANDLER_SETTING.get(settings));

    initializeProbes();                                                       // :177

    if (addShutdownHook) { Runtime.getRuntime().addShutdownHook(...); }       // :179-192

    JarHell.checkJarHell(logger::debug);                                      // :197
    IfConfig.logIfNecessary();                                                // :203
    Security.configure(environment, ...);                                     // :207 装 SecurityManager

    node = new Node(environment) {                                            // :212 ★★
        @Override protected void validateNodeBeforeAcceptingRequests(...) {
            BootstrapChecks.check(context, boundTransportAddress, checks);    // :217
        }
        @Override protected void registerDerivedNodeNameWithLogger(String nodeName) {
            LogConfigurator.setNodeName(nodeName);                            // :222
        }
    };
}
```

**四个关键点**：

1. **`initializeNatives`（`:98`）**：
   - `Natives.definitelyRunningAsRoot()` → **root 直接抛异常**（这就是「can not run elasticsearch as root」的来源）
   - `tryInstallSystemCallFilter` / `tryMlockall` / `tryVirtualLock`
   - `Natives.trySetMaxNumberOfThreads()` / `trySetMaxSizeVirtualMemory()` / `trySetMaxFileSize()`
   - `StringHelper.randomId()` 预热 Lucene 随机数（用 `/dev/urandom`）

2. **`JarHell.checkJarHell`（`:197`）**：
   检查 classpath 上是否有**同一个类的多个副本**（不同 jar 里）。
   这是 ES 插件机制的必要保障——插件用独立 ClassLoader 加载，如果 server 的类被插件重复打包，
   会出现 `ClassCastException` 这种极难排查的问题。

3. **`Security.configure`（`:207`）**：
   安装基于 `elasticsearch.policy` 的 SecurityManager。ES 用它来做：
   - 禁止反射写 `sun.*` 内部字段
   - 限制文件读写到指定目录
   - 限制网络绑定
   源码：`server/src/main/java/org/elasticsearch/bootstrap/Security.java`

4. **`new Node(environment)` 里用了匿名子类**：
   两个钩子：`validateNodeBeforeAcceptingRequests`（跑 BootstrapChecks）和
   `registerDerivedNodeNameWithLogger`（把 nodeName 设置到日志上下文）。
   生产代码里 `Node` 是 `protected` 方法，测试框架会覆盖它们。

## 3. `Node` 构造器：模块装配（★ 最重要的一节）

文件：`server/src/main/java/org/elasticsearch/node/Node.java`，入口 `:276`

```java
protected Node(final Environment environment,
               Collection<Class<? extends Plugin>> classpathPlugins,
               boolean forbidPrivateIndexSettings) {                       // :276
    logger = LogManager.getLogger(Node.class);
    final List<Closeable> resourcesToClose = new ArrayList<>();  // 失败时统一释放
    boolean success = false;
    try {
        ...
        success = true;                                             // :624
    } catch (IOException ex) {
        throw new ElasticsearchException("failed to bind service", ex);
    } finally {
        if (!success) {
            IOUtils.closeWhileHandlingException(resourcesToClose);   // :629 ★ 构造失败要回滚
        }
    }
}
```

> **设计要点**：构造器是一个「要么全成功、要么全回滚」的大事务。
> `resourcesToClose` 记录了所有需要被释放的资源（NodeEnvironment、ThreadPool、ClusterService……），
> 任何一步抛异常，`finally` 里全部关掉。这是 ES 健壮性的体现。

**为什么 `NodeEnvironment` 必须第一个？**

```java
// :291-310
boolean nodeNameExplicitlyDefined = NODE_NAME_SETTING.exists(tmpSettings);
Consumer<String> nodeIdConsumer = nodeNameExplicitlyDefined ?
        nodeId -> {} : nodeId -> registerDerivedNodeNameWithLogger(nodeIdToNodeName(nodeId));
nodeEnvironment = new NodeEnvironment(tmpSettings, environment, nodeIdConsumer);   // :295

if (nodeNameExplicitlyDefined) {
    logger.info("node name [{}], node ID [{}]", ...);
} else {
    tmpSettings = Settings.builder().put(tmpSettings)
            .put(NODE_NAME_SETTING.getKey(), nodeIdToNodeName(nodeEnvironment.nodeId()))  // :306
            .build();
    logger.info("node name derived from node ID [{}]; set [{}] to override", ...);
}
```

`nodeIdToNodeName`（`:1047`）会把 nodeId 的哈希映射到「形容词 + 漫威人物名」，
例如 `immortal-thor`、`crimson-hulk`。这个节点名会进入**每一条日志的前缀**，
所以必须在任何日志输出前确定。

`NodeEnvironment` 自己做的事：
- 校验 `path.data` 的每个条目
- 创建 `nodes/0` 目录
- 获取 `nodes/0/node.lock` 的**独占文件锁**（这就是「同一 data 目录不能被两个进程使用」的实现）
- 读取真实 nodeId（存在 `nodes/0` 下）

**`NamedWriteableRegistry`（`:414-422`）与 `NamedXContentRegistry`（`:423-430`）**

这是两个**全局注册表**，理解它们对读源码极其重要：

| 注册表 | 作用 | 内容来源 |
| --- | --- | --- |
| `NamedWriteableRegistry` | 二进制序列化时「名字 → 类」的反查 | `NetworkModule` + `IndicesModule` + `SearchModule` + 插件 + `ClusterModule` |
| `NamedXContentRegistry` | JSON/YAML 解析时「名字 → 解析器」的反查 | 同上 |

**为什么需要它们？**
ES 的 wire 协议是二进制的。`StreamInput.readNamedWriteable(Foo.class)` 只能读到「类名」，
需要注册表把类名还原成 Class 再 `new`。同理，`XContentParser` 解析 `{"match": {...}}`
时需要知道 `"match"` 对应 `MatchQueryBuilder::fromXContent`。

**这就是为什么「写一个自定义聚合/查询」必须在 `SearchPlugin` 里注册**——
不注册，序列化/反序列化就会失败。

## 4. `Node.start()`：按顺序点火（`Node.java:685`）

```java

    logger.info("starting ...");
    pluginLifecycleComponents.forEach(LifecycleComponent::start);    // :691 插件组件先起

    injector.getInstance(MappingUpdatedAction.class).setClient(client);  // :693
    injector.getInstance(IndicesService.class).start();                  // :694 ★

    injector.getInstance(RoutingService.class).start();                  // :698
    injector.getInstance(SearchService.class).start();                   // :699
    nodeService.getMonitorService().start();                             // :700
    ...
}
```

| --- | --- | --- |

| `:693` | `MappingUpdatedAction.setClient` | 循环依赖的 hack：mapping 更新要通过 client |
| `:694` | `IndicesService.start()` | 索引服务（`IndicesService.java:211`） |

| `:698` | `RoutingService.start()` | 路由服务 |

| `:709` | `GatewayService.start()` | 网关服务（状态恢复） |
| `:710-711` | `clusterService.getMasterService().setClusterStatePublisher(discovery::publish)` | ★ **把「发布」委托给 Discovery** |
| `:714-716` | `TransportService.start()` | ★ 开始监听端口 |
| `:720-732` | 读磁盘上的 `MetaData`（`GatewayMetaState.loadMetaState()`） | 供 BootstrapChecks 使用 |
| `:733-737` | `validateNodeBeforeAcceptingRequests(...)` | ★ **BootstrapChecks**：堆大小、文件描述符、mlock、发现配置…… |
| `:739` | `clusterService.addStateApplier(transportService.getTaskManager())` | tasks 也要跟状态 |
| `:741` | `discovery.start()` | ★ **必须在 clusterService.start() 之前**，因为它要设置初始状态 |
| `:742` | `clusterService.start()` | 启动 ClusterApplierService |
| `:745` | `transportService.acceptIncomingRequests()` | ★ 此刻才开始接受 Transport 请求 |
| `:746` | `discovery.startInitialJoin()` | ★ **开始选主/加入集群** |
| `:748-779` | 等待初始状态（`discovery.zen.initial_state_timeout`，默认 30s） | 用 `ClusterStateObserver` 等 `masterNodeId != null` |
| `:782-784` | `HttpServerTransport.start()` | ★ 此刻 HTTP 才开始接受请求 |
| `:786-793` | 写 `ports` 文件 | 生产环境用于服务发现 |
| `:795` | `logger.info("started")` | ★ 这行日志出现 = 节点就绪 |
| `:797` | `ClusterPlugin.onNodeStarted` | 插件回调 |

### 4.1 三个「就绪点」的区别（务必分清）

```
new Node(...) 完成   → "initialized"
   · 所有对象已创建，但端口未监听
   · 只能被本地单元测试使用

Node.start() 跑到 :745 transportService.acceptIncomingRequests()
   · ★ Transport 端口开始接受 RPC
   · ★ 但仍不能响应 HTTP

Node.start() 跑到 :782 HttpServerTransport.start()
   · ★ HTTP 端口开始接受请求
   · 但集群可能还没有 master（如果 initial_state_timeout=0）

Node.start() 跑到 :795 "started"
   · ★ 集群已有初始状态（或等待超时）
   · 这才是真正「就绪」
```

**K8s 探针建议**：用 `GET /_cluster/health?wait_for_status=yellow` 而不是 `GET /`，
因为 `GET /` 在 `:782` 就返回 200 了，此时集群可能还没选主。

### 4.2 `BootstrapChecks`：上线前的最后一道关卡

调用链：`Node.start():733` → `validateNodeBeforeAcceptingRequests`（`Bootstrap.java:214`）→ `BootstrapChecks.check(...)`

文件：`server/src/main/java/org/elasticsearch/bootstrap/BootstrapChecks.java`

| 检查 | 触发条件 | 报错关键词 |
| --- | --- | --- |
| Heap 大小 | 绑定到非 loopback 地址且 heap < `bootstrap.system_call_filter` 要求 | `initial heap size not set` |
| File descriptor | 绑定非 loopback 且 `ulimit -n` < 65535 | `max file descriptors` |
| Memory lock | `bootstrap.memory_lock=true` 但没锁住 | `memory locking requested` |
| System call filter | 启动失败 | `system call filter check failed` |
| Max map count | `vm.max_map_count` < 262144 | `max virtual memory areas` |
| Discovery 配置 | `minimum_master_nodes` 未设置 & 多节点 | `minimum_master_nodes` |
| Max size virtual memory | 无限 | |
| Max number of threads | 太小 | |
| Serial collector | 用了 Serial GC | `Serial collector` |
| OnError / OnOutOfMemoryError | 未设置 | |

> **对云服务工程师的意义**：客户报「启动失败」时，90% 是这十项之一。
> 每个检查的代码都很短，直接读 `BootstrapChecks.java` 就能给出精确答复。

## 5. 关闭流程

### 5.1 `Node.stop()`（`:802`）

```java
private Node stop() {
    if (!lifecycle.moveToStopped()) { return this; }
    logger.info("stopping ...");

    injector.getInstance(ResourceWatcherService.class).stop();               // :808
    if (NetworkModule.HTTP_ENABLED.get(settings)) {
        injector.getInstance(HttpServerTransport.class).stop();              // :810 ★ 先停 HTTP
    }
    injector.getInstance(SnapshotsService.class).stop();                     // :813
    injector.getInstance(SnapshotShardsService.class).stop();                // :814
    injector.getInstance(IndicesClusterStateService.class).stop();           // :816 停止响应状态变更
    injector.getInstance(Discovery.class).stop();                            // :819 ★ 早停，避免被别的节点误判
    injector.getInstance(RoutingService.class).stop();                       // :821
    injector.getInstance(ClusterService.class).stop();                       // :822
    injector.getInstance(NodeConnectionsService.class).stop();               // :823
    nodeService.getMonitorService().stop();                                   // :824
    injector.getInstance(GatewayService.class).stop();                       // :825
    injector.getInstance(SearchService.class).stop();                        // :826
    injector.getInstance(TransportService.class).stop();                     // :827 ★ 最后停 Transport
    pluginLifecycleComponents.forEach(LifecycleComponent::stop);             // :829
    injector.getInstance(IndicesService.class).stop();                       // :832 ★ 最末，等资源释放
    logger.info("stopped");
    return this;
}
```

**关闭顺序的设计原则**：
1. **先停入口（HTTP）**，让新请求进不来。
2. **早停 Discovery**（`:819` 注释说得很清楚）：不停的话它还在响应 ping，
   其他节点会以为它还活着，导致 `master` 变更延迟。
3. **最后停 `IndicesService`**（`:832` 注释）：它要等所有资源（scroll、recovery、shard lock）真正释放。
4. **`TransportService` 在 `IndicesService` 之前停**：不再接受跨节点请求，但本地还在收尾。

### 5.2 `Node.close()`（`:842`）——真正的资源释放

`close()` 用 `StopWatch` 给每个组件计时，最终打印「Close times for each service」。
顺序（`:851-919`）：

```
node_service → http → snapshot_service → client → indices_cluster
→ indices → indices_store → routing → cluster → node_connections_service
→ discovery → monitor → gateway → search → transport
→ plugin(...) → script → thread_pool(shutdown / awaitTermination 10s / shutdownNow)
→ node_environment → page_cache_recycler
→ IOUtils.close(toClose)
```

**关键点**：

- `:843-845`：如果还在 started，先 `stop()`。
- `:838-840` 的注释解释了一个重要细节：
  `close()` 是 `synchronized` 的，因为并发调用时，**所有调用都必须等 shutdown 完成**，
  否则 `Bootstrap.setup` 注册的 shutdown hook 可能提前终止进程。
- `:899-909`：ThreadPool 的关闭分三步——
  `shutdown()` → `awaitTermination(10s)` → `shutdownNow()`。
  这就是为什么 ES 关机有时会「卡 10 秒」。

### 5.3 三处触发关闭的入口

| 触发源 | 调用链 |
| --- | --- |
| `Ctrl+C` / `kill -15` | JVM ShutdownHook（`Bootstrap.setup:180`）→ `IOUtils.close(node, spawner)` |
| Windows 控制台关闭事件 | `initializeNatives:122` 的 `ConsoleCtrlHandler` → `Bootstrap.stop()` |
| 代码调用 | `Node.close()` |

### 5.4 `Bootstrap.stop()`（`:273`）与 `keepAliveLatch`

```java
static void stop() throws IOException {
    try {
        IOUtils.close(INSTANCE.node, INSTANCE.spawner);
    } finally {
        INSTANCE.keepAliveLatch.countDown();     // 让 keepAliveThread 退出 → JVM 退出
    }
}
```

**这个设计很巧妙**：`main` 方法返回后 JVM 之所以不退出，是因为 `keepAliveThread`
是非守护线程且在 `await()`。所有正常关闭路径最终都会 `countDown()`，让线程结束、JVM 退出。

## 6. 生命周期抽象（`LifecycleComponent`）

ES 的组件都是「四态」的：

```
        ┌─────────────┐
        │ unstarted   │
        └──────┬──────┘
               │ start()
        ┌──────▼──────┐
        │  started    │◄────┐
        └──────┬──────┘     │
               │ stop()     │ start()（幂等）
        ┌──────▼──────┐     │
        │  stopped    │─────┘
        └──────┬──────┘
               │ close()
        ┌──────▼──────┐
        │  closed     │   （不可逆）
        └─────────────┘
```

关键类：

| 类 | 路径 | 作用 |
| --- | --- | --- |
| `Lifecycle` | `common/component/Lifecycle.java` | 状态机（`moveToStarted()` 等，线程安全） |
| `LifecycleComponent` | `common/component/LifecycleComponent.java` | 接口，含 `start/stop/close/addLifecycleListener` |
| `AbstractLifecycleComponent` | `common/component/AbstractLifecycleComponent.java` | 模板实现，子类只需实现 `doStart/doStop/doClose` |

**读源码时的价值**：看到任何类继承 `AbstractLifecycleComponent`，
就知道它的 `doStart()` 是「启动时做什么」，`doStop()` 是「停止时做什么」。
这能让你在庞大的代码里快速找到切入点。
