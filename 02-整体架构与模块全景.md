## 1. 先看全局：ES 到底是什么

一句话：**Elasticsearch 是 Lucene 的分布式外壳。**

```
┌──────────────────────────────────────────────────────────────────────────┐
│                          Elasticsearch 6.6.1                              │
│                                                                           │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │  分布式能力（ES 自己实现的）                                       │   │
│   │   · 分片（Sharding）与副本（Replication）                          │   │
│   │   · 集群状态与元数据（ClusterState / MetaData）                    │   │
│   │   · 选主与故障检测（ZenDiscovery）                                 │   │
│   │   · 节点间 RPC（Transport / Netty）                                │   │
│   │   · 分片分配与再平衡（AllocationService）                          │   │
│   │   · 写入持久化（Translog）与恢复（Recovery）                       │   │
│   │   · 一致性（seqno / primary term / checkpoint）                    │   │
│   │   · 查询编排（Query Then Fetch）与聚合归并                          │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                      │
│                                    ▼                                      │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │  Lucene 7.6.0（ES 只是调用方）                                     │   │
│   │   · 倒排索引 / 文档存储 / DocValues / 列式存储                      │   │
│   │   · 段（Segment）与段合并（Merge）                                 │   │
│   │   · 查询执行（IndexSearcher / Collector / Scorer）                 │   │
│   │   · 分析器（Analyzer / Tokenizer / TokenFilter）                   │   │
│   │   · 相似度打分（BM25）                                             │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                                                           │
└──────────────────────────────────────────────────────────────────────────┘
```

**关键推论**：
1. ES 源码中**所有**「存储、索引、检索」的核心能力都是 Lucene 的。
   ES 的价值在「如何把 Lucene 组织成一个能横向扩展、能容错的分布式系统」。
2. 所以 ES 源码里最多的代码不是算法，而是**状态管理、并发控制、错误处理**。
3. 读 ES 源码的重点是**「调度」而非「算法」**。

### 3.1 顶层目录

**「module」vs「plugin」的区别（6.6.1）**：

| | modules | plugins |
| --- | --- | --- |
| 分发 | 随发行版**默认内置** | 需要**手动安装**（`bin/elasticsearch-plugin install`） |
| 依赖 | 不能引入外部 jar（除指定白名单） | 可以引入外部 jar |
| 例子 | `transport-netty4`、`analysis-common`、`lang-painless`、`reindex`、`percolator`、`parent-join` | `analysis-icu`、`repository-s3`、`discovery-ec2` |

> **关键**：ES 6.6.1 的 HTTP 与 Transport 网络实现**不在 `server` 里**，
> 而在 `modules/transport-netty4`。这是读源码时最容易踩的坑之一。

**为什么依赖注入顺序如此重要？**
`new XxxService(...)` 的构造顺序就是依赖顺序。`NodeEnvironment` 必须最先（因为它生成 nodeId，
而 nodeId 影响 nodeName 和日志）；`ClusterService` 必须在 `ClusterModule` 之前（要被 bind 进去）；
`RestController` 由 `ActionModule` 产生，然后传给 `NetworkModule`（HTTP 需要它来分发请求）。

## 5. 一次请求的"全栈"路径（把三条主线串起来）

以 `POST /myindex/_doc/1 {"name":"es"}` 为例：

```
┌─ L1 网络层（Netty IO 线程）─────────────────────────────────────────────┐
│  Netty4HttpRequestHandler.channelRead0                                 │
│    → Netty4HttpServerTransport.dispatchRequest                         │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L2 REST 层（http 线程池）──────────────────────────────────────────────┐
│  RestController.dispatchRequest(request, channel, threadContext)       │
│    → 按 method+path 找到 RestIndexAction                               │
│    → BaseRestHandler.handleRequest → RestIndexAction.prepareRequest    │
│    → client.index(IndexRequest, listener)                              │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L3 客户端与 Action 层 ─────────────────────────────────────────────────┐
│  NodeClient.index → AbstractClient.index → execute(IndexAction.INSTANCE)│
│    → NodeClient.executeLocally(action, request, listener)              │
│    → TransportAction (TransportIndexAction) 被调用                     │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L4 复制框架层（write 线程池）───────────────────────────────────────────┐
│  TransportReplicationAction.doExecute（:171）                          │
│    → ReplicationOperation.execute()                                    │
│      → primary.perform → shardOperationOnPrimary                       │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L5 分片层 ─────────────────────────────────────────────────────────────┐
│  IndexShard.applyIndexOperationOnPrimary（:715）                        │
│    → acquirePrimaryOperationPermit（:2348）                            │
│    → IndexShard.index（:779）→ InternalEngine.index（:867）             │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L6 引擎层 ─────────────────────────────────────────────────────────────┐
│  InternalEngine.index                                                  │
│    → resolveDocVersion（:725）版本冲突判定                              │
│    → LiveVersionMap 检查（realtime get 用）                            │
│    → indexIntoLucene（:1074）→ Lucene IndexWriter.addDocument          │
│    → Translog.add（:524）写事务日志                                     │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L7 副本复制（网络层，其他节点）──────────────────────────────────────────┐
│  ReplicationOperation 并发发 ReplicaRequest → 各副本 TransportReplicationAction│
│    → IndexShard.applyIndexOperationOnReplica（:722）                   │
│    → 返回 ack → 更新 local checkpoint → 推导 global checkpoint          │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
┌─ L8 集群状态线（可能触发）───────────────────────────────────────────────┐
│  若是 auto-create-index：MetaDataCreateIndexService                     │
│    → ClusterService.submitStateUpdateTask（:275）                      │
│    → MasterService.runTasks（:185）→ 新 ClusterState                   │
│    → ZenDiscovery.publish（:327）→ 广播 → 所有节点 apply                │
└───────────────────────────┬────────────────────────────────────────────┘
                            ▼
                   BulkResponse / IndexResponse → 返回到 Netty → HTTP 200
```

**注意 L1→L2 的线程切换**：Netty IO 线程不会执行业务逻辑，
`Netty4HttpServerTransport` 会把请求交给 `http` 线程池（`ThreadPool.Names.HTTP`）。
这是 ES 避免 IO 线程被阻塞的关键设计。

## 6. 线程模型（读源码时必须时刻记住）

ES 有 **几十个线程池**，定义在 `server/src/main/java/org/elasticsearch/threadpool/ThreadPool.java`。核心的几个：

> 下表参数**直接取自** `ThreadPool.java:174-193`（6.6.1 真实代码）。
> ⚠️ **注意**：6.6.1 **没有名为 `bulk` 的线程池**。它在 6.3 时被改名为 `write`，
> `ThreadPool.java:176` 写作 `new FixedExecutorBuilder(settings, Names.WRITE, "bulk", availableProcessors, 200)`——
> 第 3 个参数 `"bulk"` 是 **fallbackName**（`FixedExecutorBuilder.java:67`），
> 即 `thread_pool.bulk.*` 作为已废弃的兼容配置仍然生效，但池子的真名是 `write`。

| 线程池 | 类型 | 默认大小 / 队列 | 用途 | 关键源码 |
| --- | --- | --- | --- | --- |
| `generic` | scaling | 4 ~ `4*CPU`，keep 30s | 通用后台任务（`ClusterStateUpdateTask` 默认执行器） | `ThreadPool.java:174` |
| `index` | fixed | CPU 个，queue 200（**deprecated 标记**） | 索引/删除的分片级执行 | `ThreadPool.java:175`、`TransportIndexAction:57` |
| `write` | fixed | CPU 个，queue 200 | 写入（bulk 的分片级执行） | `ThreadPool.java:176`、`TransportShardBulkAction:94` |
| `get` | fixed | CPU 个，queue 1000 | realtime get / termvectors | `ThreadPool.java:177`、`TransportGetAction:52` |
| `analyze` | fixed | 1 个，queue 16 | `_analyze` API | `ThreadPool.java:178` |
| `search` | auto-adjusting | `searchThreadPoolSize(CPU)`，queue 1000 | 查询执行 | `ThreadPool.java:179` |
| `search_throttled` | auto-adjusting | 1 个，queue 100 | 被节流的搜索（ML/rollup） | `ThreadPool.java:181` |
| `management` | scaling | 1 ~ 5，keep 5min | 集群管理（`_cluster/*`） | `ThreadPool.java:183` |
| `listener` | fixed | `min(10, CPU/2)`，**queue -1（无界）** | 异步 listener 回调 | `ThreadPool.java:186` |
| `flush` | scaling | 1 ~ 5，keep 5min | flush | `ThreadPool.java:187` |
| `refresh` | scaling | 1 ~ 10，keep 5min | refresh | `ThreadPool.java:188` |
| `warmer` | scaling | 1 ~ 5 | IndexWarmer | `ThreadPool.java:189` |
| `snapshot` | scaling | 1 ~ 5 | 快照数据写入 | `ThreadPool.java:190` |
| `fetch_shard_started` | scaling | 1 ~ `2*CPU` | 分片恢复 phase1 | `ThreadPool.java:191` |
| `force_merge` | fixed | 1 个，**无界** | force merge | `ThreadPool.java:192` |
| `fetch_shard_store` | scaling | 1 ~ `2*CPU` | 分片恢复 store 阶段 | `ThreadPool.java:193` |
| `same` | direct | — | 当前线程直接执行 | `ThreadPool.java:215` |

此外还有由 `NetworkModule`/`SnapshotsService` 注册的：`snapshot_meta`（串行 1 个）、
`http_server_worker`、`transport_worker`。

**线程类型（`ThreadPoolType`）**：
- `fixed`：固定线程数 + 有界队列（可配置 `queue_size`），队列满则**拒绝**（rejected）
- `scaling`：`min ~ max` 之间弹性伸缩，`keep_alive` 决定回收
- `direct`：不排队，直接在当前线程执行（如 `same`）

**必须理解的 3 件事**：
1. **一个方法调用可能跨线程**。看到 `threadPool.executor(...).execute(...)` 就要警惕。
2. **`ThreadContext` 是跨线程传递上下文的唯一方式**（traceId、`X-Opaque-Id`、header）。
   见 `common/util/concurrent/ThreadContext.java`。
3. **线程池队列满了会拒绝**（`EsThreadPoolExecutor.rejectedExecution`），
   表现为 `EsRejectedExecutionException`，HTTP 返回 429。
   这是线上最常见的告警，源码在 `common/util/concurrent/EsThreadPoolExecutor.java`。

## 7. 数据流全景：从磁盘上看 ES

```
path.data/
└── nodes/
    └── 0/                              ← node.lock 在这里（NodeEnvironment 独占）
        └── indices/
            └── <indexUUID>/            ← 不是索引名！是 UUID
                └── 0/                  ← shardId
                    ├── index/          ← Lucene 目录
                    │   ├── segments_N          Lucene commit 点
                    │   ├── _0.cfs / _0.si      Segment 文件
                    │   └── write.lock
                    ├── translog/
                    │   ├── translog-1.tlog
                    │   ├── translog.ckp        ← Checkpoint（translog 与 lucene 的对齐）
                    │   └── translog-2.tlog
                    └── _state/
                        └── state-0.st      分片状态（ShardStateMetaData）
```

**这三样东西的关系**（读源码前必须建立）：

| 文件/目录 | 谁维护 | 作用 | 源码 |
| --- | --- | --- | --- |
| `index/segments_N` | Lucene | 最后一次 commit 的段清单。这是"持久化的真身" | Lucene |
| `translog/translog-N.tlog` | ES | 记录 commit 之后的所有写操作，用于崩溃恢复 | `index/translog/Translog.java` |
| `translog/translog.ckp` | ES | `{offset, numOps, generation, minSeqNo, maxSeqNo, globalCheckpoint}` | `index/translog/Checkpoint.java` |
| `_state/state-N.st` | ES | 分片状态：`allocationId`、`primary` 标记、`indexSort` 信息 | `index/shard/ShardStateMetaData.java` |
| `nodes/0/node.lock` | ES | 防止两个进程用同一个 data 目录 | `env/NodeEnvironment.java` |

**恢复时的读顺序**：
```
1. 读 index/ segyments_N，打开 Lucene
2. 读 translog/checkpoint，知道 lucene commit 时的 translog 位置
3. 重放 checkpoint 之后的所有 translog 操作
4. 得到"完整"的索引状态
```
对应源码：`InternalEngine` 的构造 → `Translog` 恢复 → `InternalEngine.recoverFromTranslog`。

## 8. 关于「扩展点」的全景

ES 的可扩展性来自 `Plugin` 接口（`server/src/main/java/org/elasticsearch/plugins/Plugin.java`）。
它是所有扩展点的总入口，通过实现子接口声明扩展维度：

| 扩展点接口 | 能做什么 | 注册位置 |
| --- | --- | --- |
| `ActionPlugin` | 自定义 REST 接口 + TransportAction | `ActionModule`（`Node.java:475`） |
| `AnalysisPlugin` | 自定义 Analyzer/Tokenizer/TokenFilter/CharFilter | `AnalysisModule`（`Node.java:362`） |
| `MapperPlugin` | 自定义字段类型、metadata 字段 | `IndicesModule`（`Node.java:400`） |
| `SearchPlugin` | 自定义 Query/ScoreFunction/Sort/Highlighter/Aggregation | `SearchModule`（`Node.java:403`） |
| `IngestPlugin` | 自定义 Ingest Processor | `IngestService`（`Node.java:384`） |
| `ScriptPlugin` | 自定义脚本引擎、Painless 白名单 | `ScriptModule`（`Node.java:361`） |
| `NetworkPlugin` | 自定义网络层（Transport/HTTP 实现） | `NetworkModule`（`Node.java:481`） |
| `DiscoveryPlugin` | 自定义发现机制（云发现） | `DiscoveryModule`（`Node.java:528`） |
| `RepositoryPlugin` | 自定义快照仓库 | `RepositoriesModule`（`Node.java:525`） |
| `ClusterPlugin` | 自定义 AllocationDecider、ShardsAllocator | `ClusterModule`（`Node.java:398`） |
| `EnginePlugin` / `IndexStorePlugin` | 自定义存储引擎 | `Node.java:434-447` |
| `PersistentTaskPlugin` | 自定义持久化任务（ML 用） | `Node.java:541` |
| `Plugin#createComponents` | 注册自己的 LifecycleComponent（会被自动 start/stop） | `Node.java:469` |
